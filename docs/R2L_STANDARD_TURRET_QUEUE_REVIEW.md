# R2l 標準配分の砲台待ち列レビュー

## 判定

標準配分の最初の4ケースを、公開 `deliver` から同じ砲台へ渡した。待ち列の容量2件を埋めた後も、追加2件は固定された2つの受渡し枠に残り、ケースが消えたり同じケースが複製されたりしないことを確認した。

最初のケースを発射して待ち列に空きができると、次の更新で受渡し枠0のケースが一度だけ装填された。続く発射後も枠1のケースが同じ順番で装填され、待ち列の順番とケースIDの対応を保った。

## 今回確認した事実

- `createBattle` の標準配分（標準弾3、重量弾2、防護板2、高速杭1）を使用した。
- 待ち列2件、受渡し枠2件という実装上の容量境界を同じ試合状態で確認した。
- 待ち列が満杯の間、同陣営の受渡し済みケースは通常 `pickup` として提示されず、`load` も提示されない。
- 最古の待ち列ケースから発射し、空きができた次の更新で受渡し枠のケースを装填した。
- 待ち列・受渡し枠・飛翔中のケースに重複がなく、同じケースを二度装填しないことを確認した。
- 画面案内に、待ち列満杯時は発射後に自動装填されることを追加した。

## 検査の境界

今回のシナリオは砲台の待ち列と受渡し境界に絞った信頼済み配置を使っている。標準一戦の勝利、広場戦術、味方命令、敵味方30人の通常行動、正式結果・得点・ランキング、iPhone実機・試遊を完成扱いにしない。

## 結論

R2lは、R2kで確認した標準条件の配送を、砲台の容量不足が起きる状態へ一段広げた。待ち列が満杯でもケースを失わず、発射後に順番どおり再開できる物理境界と、プレイヤー向けの待機案内を固定した。次は味方命令、または敵味方の通常行動を別の小単位として確認する。
