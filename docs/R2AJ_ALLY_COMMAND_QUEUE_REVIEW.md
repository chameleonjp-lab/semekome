# R2aj 二人への指示保持・取消しと入力合成のレビュー

基準はPR #71（R2ai）取り込み後のmain `e113999dcc12b6332c4cde7ca5d4ef3f42c2430c`。得点・ランキングの接続値が未確定のため、今回は既存の味方指示の入力境界を整える。

## 問題と修正

画面の単一 `pendingAllyCommand` は、次の戦闘更新前にP2/P3を続けて押すと先の指示を上書きしていた。画面側の専用待機列へ置き換え、対象別に1件・合計2件を独立に保持する。シミュレーションには既存の `AllyCommand` をP2→P3の固定順で1更新1件だけ渡す。

反映前に同じ人を再度押す場合は、その人への指示だけを取り消す。取消しのために補給復帰命令を送り直すことはなく、運搬割当の不要な初期化を避ける。反映後の守備解除は従来どおり補給復帰命令を送る。待機中・取消し可能という表示を押下直後に更新する。

|境界|待機中の指示の扱い|
|---|---|
|試合ID変更、P1死亡/世代変更|両方を破棄|
|対象の死亡/世代変更|その対象分だけを破棄|
|停止、説明、非表示、観戦、終局、画面破棄|既存の入力解放と待機列の検証で破棄|
|同じ対象の再押下|その対象分だけを取り消し|
|同じ更新に二人の指示|P2→P3、1更新1件、消費済みを再送しない|

## 独立レビュー

ユーザー指定の役割分担に従い、実装担当GPT-6.1 Sol Maxと独立レビュー担当GPT-6.1 Sol Extra Highで確認した。レビュー担当は共有ファイルを読み取り、修正は実装側が行った。

- **中程度・修正済み：攻撃と突進の同時予約で味方指示も消える。** 両行動が同じ入力に含まれると物理APIが入力全体を拒否するため、待機列から取り出したP2指示まで失われることを実`stepBattle`で再現した。`canStartAttack`/`canStartDash`を相互排他にし、先に受け付けた行動を保持する。両押下順の再検査で拒否なくP2→P3の指示が届くことを確認した。
- **検査上の問題・修正済み：接触fixtureの攻撃対象が準備中に外れる。** E29の通常AIが初回更新でP1を押し戻すため、fixture限定のE29待機と将来の判断時刻を追加した。60回の更新でも接触とP1体力4を保持することをレビュー担当が確認した。通常初期配置の検査にはこの待機を使わない。

完成版の待機列、個別取消し、固定順、試合・世代検証、停止・観戦・終局・画面破棄時の解放と追加browser4ケースを再レビューし、未解決の重大・中程度の問題はない。レビュー担当による実死亡・復活の境界検査2/2も通過した。browserケースは静的レビュー後にQuality #459で実行し、Chromium/WebKit全66件の合格を確認した。

## 維持する条件と残件

シミュレーションの単一命令API・拒否規則・AI判断・物理接触・通常初期配置・標準配分は変更していない。敵30人の1,200 tick復活、P1の300 tick観戦復活、外装7部位・7門・コアの有効突進による勝敗を維持する。待機列の固定順と同時行動の先着保持は画面側の実装判断であり、正式な命令優先順位の承認ではない。

正式な味方命令の優先順位・対象指定・別室救援、補助型と編成の完成、敵味方全員の通常行動と相互侵入、採用対向配置の複数回走破、得点式の承認とランキング実登録・外部送信、iPhone実機・試遊は未完了。R4/R5全体の完了へ読み替えない。mainへの直接push、マージ、自動マージ、保護変更、公開は行わない。
