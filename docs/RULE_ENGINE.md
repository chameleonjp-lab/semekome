# R2a 共通ルールの接続契約

## Draft PR：R3選択補給の共通砲台発射境界

PR #30で生成された共通床ケースは、`stepBattle` のP1公開コマンドを通じて通常のケース所有遷移を使う。`pickup` がケースをP1の所持枠へ移し、`load` がT1の待ち列と現在の砲台設定を記録し、`operate` がP1を有効な操作者として登録する。共有発射枠が到来すると `launchReadyTurrets` が同じケースIDの `projectile` と `Flight` を作り、ケースの `weaponId` に対応する効果を飛翔へコピーする。

今回の回帰検査では、移動AIの代わりに信頼済みのテスト配置だけを使い、床ケースをP1/T1の距離へ置く。発射後はケースが飛翔物だけから参照され、`BattleState.queued` とP1の所持枠には残らないことを `assertBattleConsistent` と合わせて確認する。共通運搬AIの全面接続、物理操作確認版との同一試合統合、P2/P3への味方命令、R3全体、通常戦の終局は未接続である。

## Draft PR：R3選択補給の共通床生成境界

`createBattle` が受け取った `playerSupplyAllocation` は、共通 `SupplySchedule` の自陣順序として保持され、`stepBattle` の `prepareCommonSupplySpawns` が4補給口へ補給口ID順に割り当てる。共通 `stepWorld` が `spawn_supply` を受け入れたケースだけ、ケースID・生成元グループ・床所在を作成し、`commitCommonSupplySpawns` が自陣カーソルを進める。今回の回帰検査はこの順序と、選択した `weaponId` が床ケースへ届くことを固定する。

敵側は独立した `SUPPLY_BAG` のスケジュールを使い、プレイヤーの選択値・予定を共有しない。床上限、停止、共通遷移の拒否ではカーソルを進めない既存契約を維持する。物理操作確認版の固定座標・時計・ケース所在、共通運搬AIの全面接続、P2/P3への味方命令、R3全体、通常戦の終局はこの単位に含めない。

## Draft PR：R3選択補給の物理配送・発射境界

出撃準備画面で検証した `playerSupplyAllocation` は、物理 `createBattle` の自車バッグへ入り、補給口の共通 `spawn_supply` 検証を通った後に実物ケースになる。`tests/rules/r3-player-supply-flow.test.ts` はそのケースをP1が拾い、物理距離・見通しと共通 `reserve_delivery` を通して砲台の受渡し床へ置き、自動装填・P1の操作位置確認・共有発射枠を通ることを確認する。発射後は同じケースIDと由来グループを保ったまま `split_payload` の分裂処理へ進む。

この境界で敵の予定を返すAPIや、共通側のプレイヤー配送AIは作らない。P2/P3の味方命令はR4の別単位とし、共通 `stepWorld` と物理 `stepBattle` を同じ試合へ重ねない。全面配送、R3全体、通常戦の終局、観戦・結果・ランキングは未完了である。

PR #4のR2aは8武器の共通ルール層であり、通常戦を遊べる完成版ではない。PR #5は別の物理処理による4種の運搬・砲撃の操作確認画面を追加する。以下の `createBattle` / `stepBattle` と `BattleState` はPR #4の契約を保持し、この画面からはまだ呼ばない。

## Draft PR：R3補給配分の検証と自車プレビュー

共通 `createBattle` は任意の `playerSupplyAllocation` を受け取れるが、`SupplySchedule` の生成境界で8個の列を検証する。列には異なる4種類だけを含め、各種類は1〜3個、合計は8個とする。指定しない場合は標準配分（標準3・重量2・防護2・高速1）を使う。敵スケジュールは標準配分を別に生成し、プレイヤーの設定や予定を敵側・画面側へ共有しない。

`getPlayerSupplyPreview` は自車カーソルの次の2個を読み取るだけの参照APIである。8個目の直後は次周期の先頭を含めて返すが、カーソル・補給口時刻・床ケースを変更しない。補給選択画面、物理操作確認版への設定反映、全面配送、特殊効果の共通実運用、通常戦の終局は別単位として残す。

## Draft PR：R3共通補給スケジュール生成器

`src/logistics/supply-schedule.ts` は、シード・陣営・周期・8個の配分から、一車両で共有する決定的な補給順を生成する。標準配分は `SUPPLY_BAG` の標準3・重量2・防護2・高速1で、同じ入力なら同じ順序を返す。`advanceSupplySchedule` は一個の成功消費だけを進め、8個目の後は次周期を自動生成する。配分の長さとケースIDは生成時に検証し、未知のケースや7個以下の不完全な配分を受け付けない。

物理 `spawnSupply` は、4補給口を陣営・補給口ID順に走査し、共通 `spawn_supply` の受入れ後だけ既存の物理バッグカーソルを進める。補給妨害、設備停止、床上限、床セル不足、共通遷移拒否では順番を保持する。再開後は過去の待ち時間を埋め合わせず、補給口ごとの次回時刻から一個だけ作る。共通生成器は順序だけを所有し、床上限・座標・ケース所在・物理時計は `physical-battle.ts` が所有するため、共通 `stepWorld` との二重生成を作らない。

この単位は共通スケジュールの生成器と物理補給への接続までであり、共通 `WorldState` の自動床配置、補給選択画面、全面的な配送AI、R3全体、通常戦の終局を完成扱いにしない。

## Draft PR：R3配送先の再選択

物理 `processCarrierAI` は、運搬中ケースの配送予約先が現在も受け入れ可能かを、物理側の設備準備状態とauthored floorの受渡し枠で再確認する。停止中・対象消失・全枠占有で予約が無効になった場合は、共通予約を解放してケースを同じ運搬手の `carried` へ戻し、同じ陣営の別砲台へ `reserve_delivery` を再実行する。候補がない更新ではケースをその場で保持し、床や停止設備への瞬間移動を行わない。

候補の順序は、同じケースの有効な予約先、現在の運搬タスクの対象、由来補給口に対応する砲台、残りの自陣砲台をID順にした決定的なものとする。キューが満杯でも受渡し床が空いていれば、既存の2枠 handoff 契約を維持して受け入れる。逆に受渡し枠が全て占有されている砲台は候補から外す。物理側が選んだ砲台を `deliverCase` へ渡し、近接した別砲台への暗黙の差し替えを許さない。

この境界は配送先の物理再選択であり、共通側が補給スケジュールや経路を自動生成する全面接続ではない。`stepWorld` の時計・乱数・履歴は物理 `stepBattle` へコピーせず、共通予約の受入れ・解放後もケース所在一意性を検査する。

## PR #6 のR2b接続境界

`src/simulation/r2b-bridge.ts` が物理処理から共通ルールへ渡す唯一の初回接続である。物理側の `BattleState` と固定座標を読み取り、次の証拠を同じ更新のスナップショットとして照合する。

- 試合ID、更新番号、人物ID、生存世代、固定座標とセル投影が一致していること。
- 核への最初の接触が `dash` であり、対象城が敵城、人物が対象城の核室にいること。
- 7門がすべて開き、通過室と門履歴が採用経路の順序どおりであること。
- 核までの固定線分が床・開門・設備の当たり判定と見通しを満たすこと。

検証に通った場合だけ `CoreAttackInput` を返し、`hit` フラグや座標を外部から信用しない。返された入力は呼出側が `stepWorld` に一度だけ渡す。橋渡し自身は時計と状態を変更しないため、物理更新と共通更新の二重進行を作らない。対象が壁・門・人物、通常接触、古い世代、古い固定位置であれば入力を返さない。

広場の `preparePlazaEntry` は、対象城側の `canGuardPlaza` 人物を実際の広場所在から導出し、全員の世代を証拠と照合する。生存護衛が残る場合は `guards_remaining`、世代がずれる場合は `stale_generation` として拒否する。全員が倒れている場合だけ、`actor:generation` をキーに `PlazaCrossingState` と `move_actor(toRoomId: "entry")` を準備する。準備は時計を進めず、同じ `stepWorld` 更新で通過入力を消費する。

これはR2bの接続土台であり、人物同士の被弾・突進、実際の広場座標、補給効果と敵判断、観戦・復活画面を実装済みとは扱わない。

## PR #7：R2b接続基盤の一更新

PR #7では、PR #6の検証関数を物理操作確認の固定更新へ接続した。`BattleIntent.bridge` は物理スナップショットの証拠だけを受け取り、`prepareR2bWorldInput` が検証済みの `CoreAttackInput` または `MoveActorInput` へ変換する。物理 `stepBattle` は物流・砲撃を処理した後、同じ現在更新番号のスナップショットへ `stepWorld` を一度だけ呼び、その結果の共通状態とイベントだけを取り込む。

物理側が更新番号・乱数・イベント履歴の所有者であるため、橋渡し用の `stepWorld` が返す次の更新番号、乱数、`lastStep`、履歴は物理状態へコピーしない。最終的な更新番号と乱数は物理側で一度だけ進める。共通側で核一撃が確定した場合は、その終局状態を物理側へ取り込み、終局イベントを重複発行しない。橋渡しの照合失敗または共通側の拒否は物理更新を止めず、既存の拒否理由へ変換して記録する。

この変更で「物理結果を検証せずに共通命中へ変換する」経路と、二つの時計を同じ試合へ重ねて呼ぶ経路を作らない。人物同士の被弾・突進、実広場座標、補給効果・敵判断の接続、観戦画面、結果・ランキングは引き続き未実装であり、PR #7を通常戦完成とは扱わない。

## PR #8：人物接触の被弾境界

PR #8では、物理固定座標の人物同士の接触を `actor_contact` 証跡として同じ更新へ接続した。証跡は攻撃側・対象側の試合ID、更新番号、世代、固定座標、同じ城の室、最初の接触が `dash` の人物であることを照合し、人物半径の重なりと床の見通しを満たす場合だけ、対象への `DamageActorInput(amount: 1)` を作る。歩行の通常接触、味方、壁越し、復活保護中・被弾無敵中、古い座標・世代、対象の城や室が異なる証跡は拒否する。

対象が生存していれば共通側で36更新（0.6秒）の追加損傷無敵を設定し、証跡に対象の選択中ケースがある場合は一個だけ床へ落とす。対象が倒れた場合は共通側の死亡・全荷物落下・予約解除・復活予約を使う。物理側は同じ更新でケースを固定座標へ戻し、対象を0.6床単位だけ押し戻す。橋渡しは物理移動・AI後、補給装填・発射より前に一度だけ行うため、接触で倒れた人物を同じ更新の射手として扱わない。

これは被弾と状態境界を先に接続する変更であり、12更新の突進移動・54更新の再使用待ち、設備への突進損傷、内部兵の実移動、実広場の連続座標、補給効果・敵判断、観戦・結果・ランキング画面は残件である。PR #8を通常戦完成とは扱わない。

## PR #9：突進実行器と接触証跡の自動生成

PR #9では物理側の `BattleIntent.dash` を実際の固定更新へ接続した。開始時の方向を捕捉し、1.2床を12更新（1更新100固定単位）で進め、開始更新から54更新の再使用待ちを持つ。通常歩行入力は突進中に混ざらず、壁・閉門・設備の手前で当たり判定を止める。

突進の掃引区間で最初に重なった敵人物はその地点で停止し、対象世代・固定位置・選択中ケースを束ねた `actor_contact` 証跡を自動生成する。核室へ入った場合は `core_contact` 証跡を生成し、いずれも既存の `prepareR2bWorldInput` と共通 `stepWorld` を同じ更新で一度だけ消費する。損傷量・押し戻し・勝敗の権威は引き続き共通側にあり、設備への10損傷、内部兵の突進、実広場の連続座標、操作確認画面への突進ボタンは残件である。

## PR #10：設備接触の耐久・停止・復旧

PR #10では、PR #9が当たり判定だけで停止していた砲台・補給口へ設備ランタイムを追加した。`BattleTurretState` と `BattlePortState` は計画書の耐久60と停止期限をそれぞれ保持し、突進掃引の最初の設備接触を固定矩形の入口時刻で決定する。敵設備に接触したときだけ `dash_equipment_damage`（10）を一回適用し、耐久が0になった更新から480更新の `disabledUntilTick` を設定する。同じ更新の別入力や停止中の接触で追加損傷は発生しない。

停止中は砲台の自動装填・発射と補給口の補給生成を抑止する。既存の補給妨害時計・外部停止時計とは別に保持するため、停止中の待ち列と次回補給時刻を詰め替えない。期限の次更新で耐久を60へ自動復旧し、`equipment_restored` を一度だけ記録する。味方設備は物理障害物として突進を止めるが損傷イベントを発生させない。人物損傷・核候補は既存のR2b橋渡しへ渡し、設備損傷は物理操作確認状態だけで完結する。

|武器内容|`src/content/weapons.ts` / `ORIGINAL_CASES.json`|8武器を重量・耐久・速度・損傷・効果へ変換。不正な効果は拒否|

|近接操作|`battle-actions.ts`|同じ城・室・距離、所持品、重量、空き、担当射手、操作権を確認。AIも共用|
|砲撃|`artillery.ts`|両車独立の発射枠、経路別の区間迎撃、分裂、外装への損傷・効果を計算|

## 外部入力

`createBattle({ seed, matchId })` が新しい状態を作り、`stepBattle(state, commands)` が最大1更新だけ進める。画面の大きさ、実時間差分、描画頻度は入力しない。状態と命令はシリアライズ可能なデータ。入力元の状態を変更しない。

```ts
import { createBattle, stepBattle } from "../src/simulation/battle.ts";

let state = createBattle({ seed: 42, matchId: "match-42" });
state = stepBattle(state, [{
  kind: "operate", matchId: state.world.matchId,
  actorId: "P1", generation: state.world.actors.P1.generation,
  turretId: "T1",
}]);
// 初期位置では砲台に届かないため out_of_range。
// 成功させるために画面から座標や命中を送ってはいけない。
```

操作命令は `pickup(objectId)`、`load(objectId,turretId)`、`operate(turretId)`、`release`、`aim(turretId,route,partId)`。対象がなくなっても別対象へ自動変更しない。停止命令だけは人物を必要とせず、`pause`、`visibility(visible)`、`resume`。ページを表示し直しても明示的な再開までは時計を進めない。

所持ケースは武器IDとカタログの重量が一致し、床・所持・予約所持・待ち列・飛行・消費の一か所にだけ存在する。R1の武器IDを持たない検査用ケース／飛翔体をR2aへ暗黙変換しない。カタログは試合開始時の信頼できる設定であり、外部入力で編集する機能はない。

砲台操作を開始すると、離席・死亡・世代変更・保護で解除されるまで射出を続ける。自陣のP2/P3は内部の仲間処理から操作できるが、外部入力で本人になりすますことはできない。味方への命令はR4で追加する。射出枠は各車0、48、96…更新、準備済みの砲台を順送りする。空いた枠は持ち越さず、射出済みの弾は射手死亡でも残る。

## 時間と効果

経路は直通120／迂回156単位。飛行の `progress` は経路単位×60の整数分子で、標準弾なら毎更新20増える。発射更新には動かさず、その後360／468更新で着弾する。車内の歩行座標とは混用しない。迎撃は同じ経路の敵対弾だけ、威力に関係なく双方の耐久を1ずつ減らす。接触時刻が同じ場合はID順、接触と着弾が同時なら接触を先に扱う。

着弾の外装目標は更新開始時で選び、同更新の先の弾で壊れても後の弾を次部位へ飛ばさない。余剰損傷は繰り越さず、全壊後は外装損傷0で追加効果だけ処理する。砲弾は核を攻撃しない。

補給妨害の停止／免疫時計は360／240更新。停止と免疫の間は延長しない。設備停止は別の理由として保持し、`canSupplyProduce` は両方の解消を要求する。通路妨害は採用データの入口床を中心に、発射側ごとに一つを置き換える。`movementMultiplier` は所属に関係なくその場所の0.65と重量3の0.85を掛ける。
