# R2a 共通ルールの接続契約

PR #4のR2aは8武器の共通ルール層であり、通常戦を遊べる完成版ではない。PR #5は別の物理処理による4種の運搬・砲撃の操作確認画面を追加する。以下の `createBattle` / `stepBattle` と `BattleState` はPR #4の契約を保持し、この画面からはまだ呼ばない。

## 操作確認版との境界

|対象|共通ルール（PR #4）|物理操作確認（PR #5）|
|---|---|---|
|入口|`src/simulation/battle.ts`|`src/simulation/physical-battle.ts`|
|公開API|`createBattle` / `stepBattle`|`physicalBattle.createBattle` / `physicalBattle.stepBattle`|
|状態と命令|`domain/battle.ts` の `BattleState`、`BattleCommand[]`|`physical-battle.ts` の `BattleState`、`BattleIntent`|
|人物の位置|R1セル座標|セル中心から明示変換した1床＝1000整数座標|
|実装範囲|8武器、分裂・妨害・減速、4役割の判断|4種の補給・移動・現物運搬・受渡し・砲撃・画面|
|未接続|物理移動・補給・配送と画面|8武器の効果と共通ルールの敵判断|

両方とも独立した固定更新と時計を持つ。同じ試合へ二つの更新関数を呼ばず、状態や物体を相互へ暗黙変換しない。物理操作確認用の物体には共通ルールの必須 `weaponId` がない。共通の4種の数値が一致しても、同じ実装を呼んでいるとは扱わない。両処理の統合と特殊効果の画面接続はR2b以降の検査対象として残す。

## PR #6 のR2b接続境界

`src/simulation/r2b-bridge.ts` が物理処理から共通ルールへ渡す唯一の初回接続である。物理側の `BattleState` と固定座標を読み取り、次の証拠を同じ更新のスナップショットとして照合する。

- 試合ID、更新番号、人物ID、生存世代、固定座標とセル投影が一致していること。
- 核への最初の接触が `dash` であり、対象城が敵城、人物が対象城の核室にいること。
- 7門がすべて開き、通過室と門履歴が採用経路の順序どおりであること。
- 核までの固定線分が床・開門・設備の当たり判定と見通しを満たすこと。

検証に通った場合だけ `CoreAttackInput` を返し、`hit` フラグや座標を外部から信用しない。返された入力は呼出側が `stepWorld` に一度だけ渡す。橋渡し自身は時計と状態を変更しないため、物理更新と共通更新の二重進行を作らない。対象が壁・門・人物、通常接触、古い世代、古い固定位置であれば入力を返さない。

広場の `preparePlazaEntry` は、対象城側の `canGuardPlaza` 人物を実際の広場所在から導出し、全員の世代を証拠と照合する。生存護衛が残る場合は `guards_remaining`、世代がずれる場合は `stale_generation` として拒否する。全員が倒れている場合だけ、`actor:generation` をキーに `PlazaCrossingState` と `move_actor(toRoomId: "entry")` を準備する。準備は時計を進めず、同じ `stepWorld` 更新で通過入力を消費する。

これはR2bの接続土台であり、人物同士の被弾・突進、実際の広場座標、補給効果と敵判断、観戦・復活画面を実装済みとは扱わない。

|担当|入口・データ|責任|
|---|---|---|
|武器内容|`src/content/weapons.ts` / `ORIGINAL_CASES.json`|8武器を重量・耐久・速度・損傷・効果へ変換。不正な効果は拒否|
|操作|`src/simulation/battle.ts` の `stepBattle`|試合とP1の世代・生存・保護を確認。外部命中通知やNPCへのなりすましを拒否|
|近接操作|`battle-actions.ts`|同じ城・室・距離、所持品、重量、空き、担当射手、操作権を確認。AIも共用|
|砲撃|`artillery.ts`|両車独立の発射枠、経路別の区間迎撃、分裂、外装への損傷・効果を計算|
|敵判断|`enemy-rules.ts`|同じ部屋で分かる現在情報から役割別の意図を選ぶ。近くの取得・装填・操作のみ実行|
|基礎の確定|`world.ts` の `stepWorld`|内部損傷から外装・開門・終局・復活を確定。画面へ直接公開しない|

## 外部入力

`createBattle({ seed, matchId })` が新しい状態を作り、`stepBattle(state, commands)` が最大1更新だけ進める。画面の大きさ、実時間差分、描画頻度は入力しない。状態と命令はシリアライズ可能なデータ。入力元の状態を変更しない。

```ts
import { createBattle, stepBattle } from "../src/simulation/battle.ts";

let state = createBattle({ seed: 42, matchId: "match-42" });
state = stepBattle(state, [{
  kind: "operate", matchId: state.world.matchId,
  actorId: "P1", generation: state.world.actors.P1.generation,
  turretId: "T1",
}]);
// 初期位置では砲台に届かないため out_of_range。
// 成功させるために画面から座標や命中を送ってはいけない。
```

操作命令は `pickup(objectId)`、`load(objectId,turretId)`、`operate(turretId)`、`release`、`aim(turretId,route,partId)`。対象がなくなっても別対象へ自動変更しない。停止命令だけは人物を必要とせず、`pause`、`visibility(visible)`、`resume`。ページを表示し直しても明示的な再開までは時計を進めない。

所持ケースは武器IDとカタログの重量が一致し、床・所持・予約所持・待ち列・飛行・消費の一か所にだけ存在する。R1の武器IDを持たない検査用ケース／飛翔体をR2aへ暗黙変換しない。カタログは試合開始時の信頼できる設定であり、外部入力で編集する機能はない。

砲台操作を開始すると、離席・死亡・世代変更・保護で解除されるまで射出を続ける。自陣のP2/P3は内部の仲間処理から操作できるが、外部入力で本人になりすますことはできない。味方への命令はR4で追加する。射出枠は各車0、48、96…更新、準備済みの砲台を順送りする。空いた枠は持ち越さず、射出済みの弾は射手死亡でも残る。

## 時間と効果

経路は直通120／迂回156単位。飛行の `progress` は経路単位×60の整数分子で、標準弾なら毎更新20増える。発射更新には動かさず、その後360／468更新で着弾する。車内の歩行座標とは混用しない。迎撃は同じ経路の敵対弾だけ、威力に関係なく双方の耐久を1ずつ減らす。接触時刻が同じ場合はID順、接触と着弾が同時なら接触を先に扱う。

着弾の外装目標は更新開始時で選び、同更新の先の弾で壊れても後の弾を次部位へ飛ばさない。余剰損傷は繰り越さず、全壊後は外装損傷0で追加効果だけ処理する。砲弾は核を攻撃しない。

補給妨害の停止／免疫時計は360／240更新。停止と免疫の間は延長しない。設備停止は別の理由として保持し、`canSupplyProduce` は両方の解消を要求する。通路妨害は採用データの入口床を中心に、発射側ごとに一つを置き換える。`movementMultiplier` は所属に関係なくその場所の0.65と重量3の0.85を掛ける。

## 共通ルールへ次に接続するもの

- R2b：操作確認版の1床＝1000整数の人物位置・連続移動・壁と門の衝突を共通ルールへ接続し、人物との最初の接触、突進、被弾無敵、荷物落下、広場突破、実戦画面を統合する。共通ルール側の距離検査はR1のセル座標上の値であり、歩行の検査ではない。
- R2b：敵の `move_goal`・`defend`・`retreat` を実移動／突進へ接続。現状は意図だけ。護衛の戸口・視線・詰まりからの戻り方も未実装。
- R3：操作確認版の補給生成・受渡し・配送を共通ルールへ接続し、修理・設備への突進損傷を加える。共通ルール側の運び手が拾った現物は予約のない配送を実行せず待機。効果の停止時計と速度係数は検査済みだが、実際の補給／歩行を止める接続は未実施。
- 同更新の人物死亡と射出の順序は人物衝突接続時に統合すること。人物衝突→発射可否検査とし、AI判断周期を待たず停止する。核候補は更新開始時から集めて死亡で取り消さず、最終開門の通過は次更新から。`stepWorld` を別に呼んで時計を二度進めない。
- 操作確認版の戦闘表示・名前・カウントダウンには別の画面検査がある。共通ルール検査からそれらの合格を推測せず、結果・ランキング・実機性能も合格扱いにしない。

検査の人物位置・床上ケース・設備停止状態はテスト内で用意した明示的な初期条件。通常戦に補給生成・瞬間移動・設備破壊の機能が備わったことを意味しない。
